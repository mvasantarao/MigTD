## Design decision

Reuse the complete 220-byte `ReportDataContextV1`, byte for byte, rather than
inventing a new session-context digest or duplicating a subset of its fields.
It supplies the request ID, role, migration version, algorithm, tenant
REPORT_ID, TH1, attested contribution commitment and local policy digest.

The context in this new message is an **exact reference/copy of the context
accepted from that sender's verified MA evidence**. Repeating it does not
authenticate it. The consumer must compare it against independently verified
current-session evidence, not against another value taken from this message.

Only `MaKeyContribution` purpose is legal. No existing context purpose, field,
version, existing record layout or cryptographic construction is redefined.
The separately named Task 2/3 freeze Markdown records were unavailable during
the preceding review. This extension does not claim to reconstruct their
cryptographic formulas; those remain authoritative for later implementation.

## Codec and secret ownership

Implementation:
[key_contribution.rs](../../../src/pal/src/snp/key_contribution.rs).

- The record owns its 32-byte contribution in `Zeroizing`; it is not `Copy`
  or `Clone`, and its custom `Debug` output redacts the contribution.
- Construction takes ownership of a zeroizing contribution.
- `encode_exact()` returns a zeroizing 272-byte buffer, not an ordinary
  unguarded array.
- `decode_exact(&mut [u8])` consumes and erases the supplied payload on success
  **and** error. On success, the returned record owns the decoded secret.
- `validate_context()` compares every context field with the expected
  verified context; on mismatch it clears the owned contribution.
- `clear_contribution()` permits immediate cleanup after derivation.
  Normal drop also wipes the owned contribution via `Zeroizing`.
- The caller must erase transport copies and any separately created copies,
  clear/drop the record after derivation or failure, and never log encoded
  payloads or the borrowed contribution.

The direct `zeroize` dependency is already present in the workspace lockfile;
the only lockfile change adds it to PAL's dependency list.

## Runtime consumer contract (not activated by P0.5)

These are requirements for later handlers, not claims that the current
runtime executes them:

1. Accept this message only on authenticated, encrypted `PeerTransport`/SPDM
   in the proper contribution phase. Never route it over host control.
2. Verify MA evidence and its complete 64-byte REPORTDATA binding first,
   including the expected current context and accepted trust/processor
   profiles. A fixture report's own embedded digest is not a live-session
   binding.
3. Obtain the expected sender role from the workflow/opcode, not the payload.
   Request is source-role; response is destination-role.
4. Compare the entire message context with that sender's verified MA context.
   `validate_context()` supplies this comparison, not evidence verification.
5. Recompute the commitment from the actual 32-byte contribution using the
   frozen Task 2 construction and verified inputs. Compare it with the
   attested commitment before accepting the secret. **Equality of commitment
   references alone does not prove the contribution preimage.**
6. Track acceptance per request/session: exactly one source contribution and
   one destination contribution. Reject duplicate, reversed, out-of-phase,
   wrong-request, wrong-tenant, wrong-session or replayed messages.
7. Do not derive/install keys until all required checks and both contributions
   succeed. Clear secrets on derivation, rejection, timeout and cancellation;
   transport/error paths must clear their own copies.

Duplicate/replay tracking and commitment preimage verification need the
later authenticated exchange/runtime state and Task 10 cryptography. P0.5
does not introduce a second state machine or invent a commitment formula.
P0.8 supplies independent cryptographic vectors; the vectors added here are
wire-layout vectors with synthetic contribution/commitment bytes.

## Protocol error mapping

`SnpKeyContributionV1::codec_failure()` maps codec failures to the existing
`SnpAuthorizationFailureV1` values without allocating new statuses:

| Failure | Protocol value |
|---|---|
| Unsupported envelope/context version | `UnsupportedVersion` |
| Length overflow or configured size limit exceeded | `ResourceLimitExceeded` |
| Local writer buffer too small | `InternalError` |
| Malformed magic/type/enum/length/purpose/reserved bytes, truncation/trailing bytes and other structural failures | `MalformedMessage` |

`validate_context()` maps:

| Failure | Protocol value |
|---|---|
| Wrong expected/actual purpose | `UnexpectedMessage` |
| Wrong request or role | `ProtocolStateViolation` |
| Wrong tenant REPORT_ID | `IdentityBindingFailed` |
| Other context inequality, including TH1, commitment, policy or migration version | `ReportDataBindingFailed` |

Later runtime checks must map duplicate/out-of-phase messages to
`ProtocolStateViolation`, detected replay to `ReplayDetected`, and recomputed
commitment mismatch to `ReportDataBindingFailed`. No handler sends these
failures yet; the existing dispatcher still rejects unhandled SNP opcodes.

## Compatibility

This is an additive extension, not backward execution compatibility.
Old peers do not understand the new opcode/element/record type. There is no
new capability negotiation in P0.5, and the current outer VDM version remains
unchanged. Before runtime activation, require peers implementing this extension
or add an explicitly accepted compatibility policy. Unsupported peers must
fail, never fall back to TDX MSK messages or weaker evidence.

Existing MA/tenant/collateral/authorization vectors and limits are preserved.
P0.6 confirmation and installation-result records are not allocated here.

### Complete-evidence digest

The canonical digest is SHA-384 over the following concatenation. Domain
strings are ASCII without a trailing NUL; integers are little-endian.

```text
"SNP-LM-TENANT-EVIDENCE-v1"       25 bytes
encoding                         u16 (1 = raw AMD report, 2 = EmulatorV1)
report_length                    u32 = 1184
report                           exact 1184 bytes, including signature
supplement_length                u32 = 0 or 220
supplement                       absent or exact 220 bytes
supplement_signature_length      u32 = 0 or 96
supplement_signature             absent or exact 96 bytes
```

Only the two exact shapes are legal: raw has both zero lengths and no extra
bytes; emulator has both nonzero lengths and complete byte arrays. Preimages
are 1223 and 1539 bytes respectively. Encoding tags identify input shape, not
production/fixture trust, AMD layout authorization, or signing-key type.
Expected evidence provenance, trust and layout remain independent mandatory
verifier checks; the raw tag does not resolve the AMD physical-layout conflict.
Hashing unverified bytes confers no authority. The current bridge constructs
verified receipts only for raw reports after cryptographic verification.
AAS1A-M must authenticate the complete signed supplement before constructing
the corresponding composite receipt.

The accepted P0.5 cache reference remains `SHA384(exact_base_report[1184])`.
It is a lookup key, **not** this complete-evidence digest. A raw cache hit
authenticates no supplement; composite providers must pin and verify the
complete package. Collateral is verified separately, not silently concatenated
into the tenant-report digest.

### Delivery and message ordering

The bootstrap form was accepted without an override; the recommended default
requires **both BASE PrepareMigrationRequest messages to carry the same source
tenant evidence**, or a reference to its already-pushed local copy, before
purpose 1. BASE-to-BASE propagation is later T4.12/H5.1 integration, not an
MA-pull operation or an implemented kernel transport. Each MA resolves its
own pushed copy and verifies the entire evidence package independently.
Different valid reports with the same REPORT_ID are not interchangeable.

The required sequence is:

1. Both MAs verify the same tenant evidence; only provisional handles route it.
2. Obtain TH1 and authenticate both role-specific purpose-1 MA reports, including
   the approved MA/policy/collateral checks. Only then check REPORT_ID_MA against
   the authenticated source MA and reconstruct the common authorization context.
3. Durably reserve the exact local operation and common authorization binding.
4. Acquire and verify local purpose-2 evidence. Source sends purpose-2 MA
   evidence using existing MA request `0x20`, element `0x0100`; destination
   verifies it and returns its purpose-2 MA evidence using response `0x21`.
   Both sides verify the other's report and their own report before completing
   the reciprocal proof gate. Collateral retains `0x22/0x23`, element `0x0101`,
   with independently verified, exact report/key/trust correlation.
5. Only after both purpose-2 checks may source send the existing source-only
   tenant record `0x24`, element `0x0102`. Its context references the source's
   verified purpose-2 context; the embedded tenant base report must exactly
   match the preflight evidence. This record is not bootstrap acquisition.
   The receiver retains the complete authenticated package and checks its
   canonical digest, including any supplement, rather than replacing it with
   only the record's base-report bytes.
6. Require current firmware identity/binding/lifecycle validation and durable
   replay admission before destination emits authorization result `0x25`,
   element `0x0103`, containing the exact authorization-context digest.
   Subsequent policy, KDF, installation and readiness gates remain mandatory.

Purpose-1 and purpose-2 exchanges reuse the existing MA envelope but occupy
distinct workflow states. Neither opcode nor a repeated context authenticates
the payload by itself. Handlers must reject stale, duplicate, reordered or
wrong-purpose exchanges and must compare against locally reconstructed
expected contexts. No opcode, element, existing record length or error code
is allocated or renumbered by P0.6.

P0.11/T4.12/AAS1A-M must reconcile complete emulator MA-profile/supplement
transport with the existing base-report-only envelopes before activating
them. This addendum freezes direction, phase, authority and digest semantics,
not an unimplemented supplement wire extension. Both BASE requests carrying
the full tenant package removes the tenant bootstrap circular dependency.

### Durable replay contract and qualification boundary

The shared `pal::tenant_replay` controller requires a trusted store scoped to
a stable MA authority across restart and handoff. Capacity is a nonzero,
trusted provider configuration, not a peer-selected value. Load must check
integrity, an independently anchored rollback-resistant revision and bounded
decoding. Missing or unprovisioned state fails explicitly; no empty-journal,
filesystem or memory fallback is selected.

Every mutating transition uses revision compare-and-swap and acknowledges only
after durable storage/anchor commitment and exact authenticated readback.
Readback consistency is not itself proof of durability or anchor independence.
Storage/acknowledgement uncertainty blocks the controller until authenticated
recovery; a new controller must still validate the persistent independent anchor.

```text
Reserved -> Authorized -> Terminal(Succeeded | Aborted | Failed, result_digest)
Reserved -> Terminal(Aborted | Failed, result_digest)
```

The record pins tenant ID, complete-evidence digest, authorization digest,
both MA IDs, verifier trust, complete local operation context, stage and terminal
outcome/result digest. Same active binding returns its recorded stage without
repeating a transition. Same request with different fields, same report digest
under another operation, or another active operation for the tenant fails.
Current firmware is revalidated on first authorization and every authorization
retry. Terminal records never reserve, authorize or change again; read-only
queries may return their recorded result. New report/new request after a
terminal operation is allowed only through all normal gates. There is no
automatic eviction or tombstone cleanup, and exhaustion fails closed.
Exact-binding status lookup takes precedence over active-tenant conflict checks
and must not depend on the order in which authenticated records are restored.

Within a controller, observed revision regression, same-revision equivocation,
record removal and backward/changed-terminal state fail. Across process restart
and handoff, the independent trusted storage anchor remains mandatory.
The test model's separate image/anchor fields and controller reopen cases
qualify control flow only, not disk persistence, cryptographic sealing,
cross-process atomicity or hardware rollback resistance.
Those tests retain the verified operation binding in unit-test memory.
Real restart adapters must recover authenticated workflow context and outcomes,
or fail/abort through the specified recovery path; they cannot invent a
replacement TH1, recreate an empty journal or silently reuse lost secrets.

Actual result production, effects-once installation, policy decisions,
authoritative firmware queries, terminal result hashing, retention/cleanup,
namespace migration across rebind and resource sizing must be wired and
qualified under Tasks 7-13, Phase 4 and H5.4/H5.7. A replay `Authorized` stage
is not migration readiness or a successful firmware installation receipt.

The emulator regressions exercise the **unchanged legacy workflow**, not the
new contribution exchange. Full repository CI and hardware qualification
were not performed; no claim of live cryptographic exchange, replay-state
enforcement, key derivation or installation is made.

### Implemented transcript validator

[Contribution exchange](../../../src/pal/src/snp/contribution_exchange.rs)
requires the P0.6 reciprocal purpose-2 proof for the complete matching local
replay binding, including local operation identity. Equal authorization
digests alone do not admit a different local operation.
Role-specific purpose-1 contexts are read from the verified authorization
context; peer fields cannot supply the expected context.

```text
AwaitingSource -> AwaitingDestination -> Complete -> one-shot pair consumption
any rejection / abort -> Aborted (no resumption)
```

Each message must first match the entire verified context, then the trusted
commitment verifier must validate the actual secret against the attested
commitment and frozen Task 2 inputs. The direction comes from trusted workflow
and opcode, not a role claimed by the payload.
This models the logical transcript containing both local and remote messages;
it is not a network driver that expects both contributions from the peer.

Decoding erases the supplied payload on every outcome. Every rejection clears
all retained contributions, and no incomplete/aborted instance yields a pair.
The non-cloneable pair permits one consuming callback, always source then
destination. Owned values use the existing zeroizing record; abort explicitly
clears them and drop clears them on completion, failure or unwind. Debug output
is redacted. Caller-created copies and derived outputs remain caller-owned.
Timeout/cancellation/session loss must call abort or drop; no timer or runtime
dispatch is implemented here.

| Offset | Width | Field |

### Ordered state and explicit verification boundaries

```text
AwaitingDestinationConfirmation

 -> AwaitingPersistedState
 -> AwaitingInstallationResult
 -> Complete
any rejection / abort -> Aborted
```

The sequence consumes both local and remote messages in logical order.
The expected `SnpSessionReferenceV1` is trusted local Task 10 data, not a

waiting for success-only evidence. Duplicates cannot overwrite terminal results.
